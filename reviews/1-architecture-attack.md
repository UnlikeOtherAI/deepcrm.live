# Architecture attack review #1 — where DeepCRM breaks in production

Adversarial review of the design docs only (`docs/brief.md`, `docs/architecture.md`, `docs/schema-engine.md`, `docs/auth-and-tenancy.md`, `docs/spec/contracts.md`, `docs/spec/events.md`, `docs/spec/protocol-flows.md`, `docs/spec/templates/*.json`, `docs/spec/policy-defaults.json`). No code exists yet; every finding below is a design defect that will fire in production if built as written. Ordered roughly by severity. Each finding: severity → location → failure scenario → concrete fix.

---

## CRITICAL

### C1. `record_changes.seq` is not commit-ordered — the change-feed cursor silently and permanently drops events
**Where:** `schema-engine.md` §2 (`RecordChange.seq BigInt @default(autoincrement())`), §4 step 12; `events.md` §1–3 ("`seq` is the cursor and ordering key across all consumers"); `protocol-flows.md` F8/F11; `contracts.md` `Change.seq` ("monotonic cursor value").

**Scenario:** Postgres sequences allocate at `INSERT` time, not commit time. Txn A inserts a change row and gets `seq=1041`; txn B (on another connection) gets `seq=1042` and commits first. A pull consumer (or the `change.deliver` worker) runs `WHERE seq > 1040`, sees 1042, commits its cursor/`last_delivered_seq = 1042`. Txn A commits a millisecond later. `seq=1041` is now behind the cursor and is **never delivered** — not to `crm_changes_since` consumers, not to webhooks. The 30 s debounce on webhooks does not fix this: any transaction whose commit is delayed past the next delivery window (bulk import batch, a merge touching hundreds of link rows, lock contention) commits with a `seq` already behind `last_delivered_seq`. The doc's own guarantee ("batches are delivered in `seq` order and never overlap") is exactly what makes the loss silent. This fires most often precisely under the load where the feed matters most (bulk sync, merge storms).

**Fix:** Make `seq` order identical to commit order. Practical options, pick one and write it into the spec:
1. Per-tenant strictly-serialised sequence: replace `autoincrement()` with `UPDATE teams SET feed_seq = feed_seq + 1 WHERE id = $1 RETURNING feed_seq` executed as the **last** statement before commit inside `applyWrite`. The row lock on `teams` is held to commit, so a blocked writer's seq is always allocated after the blocker's commit → seq order == commit order. Cost: per-tenant write serialisation on one short statement; acceptable at CRM per-team write rates and it also gives a natural per-tenant feed.
2. If global seq is kept: consumers must read against a **safe watermark**, not `max(seq)`: e.g. serve only rows with `seq < (SELECT min(seq_in_flight))` maintained via a small `feed_inflight(seq, started_at)` table inserted before the change row and deleted at commit (or use `pg_current_snapshot()`-style xmin tracking). Readers then never pass a not-yet-committed lower seq.
3. Cheap-but-honest fallback: keep autoincrement, but document and implement the cursor as *high-watermark with a lag* (`seq > cursor AND occurred_at < now() - interval '15 seconds'`) **and** reconcile on each pass (re-read `seq BETWEEN cursor-1000 AND cursor` for rows first seen now). This is probabilistic; option 1 or 2 is correct.

Also fix the doc contradiction while here: `brief.md` §6.5 says cursor = `(occurred_at, id)`; `events.md` §2 says cursor = decimal `seq`. `occurred_at` is an app-clock `now()` default — non-monotonic across API hosts and equally not commit-ordered. Pick the seq-based design and delete the `(occurred_at, id)` language from the brief.

### C2. Idempotency is check-then-act with store-after-commit — concurrent duplicates and "committed but errored" writes
**Where:** `schema-engine.md` §4 step 13; `contracts.md` `IdempotencyKey` ("same key + same arguments within 24h returns the original result"); `protocol-flows.md` F4.

**Scenario 1 (duplicate side effects):** Two identical requests with the same `idempotency_key` arrive concurrently (Nessie retrying a timed-out tool call — the exact case idempotency exists for). Both look up `idempotency_replays`, both miss, both execute the full write path, both commit. Two records created. The unique-key table only saves you if the payload happens to carry a unique attribute.
**Scenario 2 (mutation applied, error returned):** The result is stored in `idempotency_replays` **after commit**. Both txns commit, then both try to insert the replay row; the second hits `@@unique([organizationId, teamId, key])` and the *client gets an error for a write that already happened*. It retries with the same key, and — if the winner's replay insert landed — gets the stored result; if the winner crashed between commit and replay-insert, it gets `IDEMPOTENCY_MISMATCH`-adjacent chaos or a second write.

**Fix:** Reserve the key **inside** the transaction: `INSERT INTO idempotency_replays (…, key, arguments_hash, result NULL) VALUES (…) ` as step 0. Unique violation ⇒ the key is in flight or done: roll back, then either (a) block on the inserting txn's outcome (`SELECT … FOR KEY SHARE` after it commits / pg_advisory lock on `hashtext(key)` taken before the insert so the loser waits, then re-reads the stored result), or (b) return a typed `IDEMPOTENCY_IN_PROGRESS` the client retries. Fill `result` in the same commit as the mutation so "applied" and "replayed" are atomic. Also include the tool name in the uniqueness/hash comparison (same args on a different tool must mismatch, not collide).

### C3. `crm_record_assert` is not sync-safe under concurrency — the F4 promise is false
**Where:** `schema-engine.md` §4 (`assert`: look up `record_unique_keys` → update else create); `protocol-flows.md` F4 ("Sync-safe upsert").

**Scenario:** Two concurrent syncs (Gmail + a CSV import) assert `anna@asahi.eu`. Both read `record_unique_keys`, both miss, both take the create branch. One commits; the other's unique-key insert (step 6) raises a unique violation. The spec defines no catch-and-retry, so the loser surfaces `DUPLICATE_FOUND` to a caller that was promised an upsert — or worse, if the violation is caught generically, the caller's *other* fields (name, company link) are silently dropped because the loser's patch is never applied. Every integration does concurrent asserts; this fires on day one.

**Fix:** Specify and implement assert as: lookup → create → **on unique violation, roll back to a savepoint and re-run as update of the conflicting record** (the conflicting `record_id` is already read back in step 6). Add an advisory lock on `hashtext(attributeId ∥ normalizedValue)` for the create branch so the common case serialises instead of exceptioning. Document the retry bound.

### C4. `block` matching rules are enforced by a non-transactional read — blocks don't block
**Where:** `schema-engine.md` §4 step 7 and §6.

**Scenario:** Matching rules are evaluated as plain SELECTs against committed state (`record_unique_keys`, `data->>slug`, trgm similarity). Two concurrent creates for "Asahi Europe Ltd" / "ASahi Europe" with the `normalized name → block` rule: both evaluate candidates before either commits, both see nothing, both insert. The rule that exists to prevent duplicates is silently violated whenever duplicates arrive concurrently — which is exactly how duplicates arrive (two agents, two sync workers). `action = warn` has the same hole but at least doesn't claim to prevent anything.

**Fix:** For `block` rules, the matched key must be *materialised and uniquely constrained*: a `record_match_keys (object_type_id, rule_position, normalized_key, record_id)` table with `@@unique([objectTypeId, rulePosition, normalizedKey])`, written in the same transaction as the record. Violation ⇒ `DUPLICATE_FOUND{candidates}` read back in-tx. `normalized`-method rules on non-unique attributes already build the `_n.<slug>` shadow — move it out of `data` into this table where the DB can enforce it. `fuzzy`/`warn` can stay non-transactional but the docs must stop implying `block` is a guarantee under concurrency.

### C5. Unmerge is impossible in the common case — restored losers collide with unique keys the merge moved to the survivor
**Where:** `schema-engine.md` §7 steps 3 and 8.

**Scenario:** Person B (`anna@asahi.eu`, unique) is merged into survivor A. Step 3 moves B's unique keys to A "where survivor lacks them". `crm_unmerge` later restores B from the snapshot — including B's `emails` value — and tries to recreate B's unique key. That key is now held by A. Unique violation. Either unmerge hard-fails (data loss: the merge is irreversible despite the feature existing), or the implementation silently strips B's email (corrupt restore). The same problem applies to list entries ("duplicate ⇒ drop the loser's" at merge; at unmerge the survivor still has the entry → `@@unique([listId, recordId])` collision) and to re-pointed links whose duplicates were collapsed. "Re-linking is best-effort and reported" (§7.8) is a weasel clause hiding the fact that unmerge-as-specified cannot satisfy its own constraints.

**Fix:** Specify the inverse explicitly: unmerge must (1) remove from the survivor every unique key whose normalized value appears in the loser's snapshot and was not in the survivor's pre-merge state, (2) remove list entries that were re-pointed from the loser (snapshot must record *which* entries/links/keys were re-pointed vs. genuinely the survivor's — today the snapshot format doesn't distinguish), (3) restore the loser's keys/entries/links from the snapshot, (4) resolve collisions against values written to the survivor *after* the merge (post-merge writes win per "changes made to the survivor are kept", and the conflict list must be returned in the `crm_unmerge` result — currently `out: { restored: [ids] }` has no conflict field). Add `conflicts: [...]` to the contract.

### C6. Merge re-points links on third-party records without locking them — unbounded lock graph, projection drift, feed gaps
**Where:** `schema-engine.md` §7 step 4 ("all `record_links` re-pointed"), §4 step 4 (locks only "records touched"), `architecture.md` §4 guardrail ("`records.data[slug]` for a `record_reference` attribute is a projection the engine maintains").

**Scenario:** B is merged into A. Every deal, activity, note and task in the tenant that links to B must be re-pointed to A. Those links are *foreign records'* data: the `record_reference` projection lives in the **from-record's** `data[slug]`. So merge must rewrite `records.data` on an unbounded set of third-party records — records it never locked (step 1 locks only survivor + losers). Consequences, pick your poison: (a) if merge updates third-party `data` without locks, a concurrent `crm_record_update` on that deal can overwrite the projection back to the loser id — permanent drift between `record_links` and `data`; (b) if merge does lock them, the lock set is unbounded ("merge this person" locks 5,000 activities) and sorted-id deadlock-freedom no longer holds because the set is discovered after the initial lock batch; (c) per C-feed semantics (finding M4 below), those third parties' timelines and the change feed never even see the re-point.

**Fix:** Decide and specify one of:
1. **Projections are derived, never stored for merge-relevant paths** — `data[slug]` for `record_reference` is computed at read from `record_links`, so re-pointing one row in `record_links` is the whole operation. (Recommended; kills an entire class of drift, costs a join.)
2. If the projection stays materialised: merge must lock third-party from-records in id order in batches, emit a change row per re-pointed projection, and cap/split the operation (merge of a record with >N inbound links becomes a Task). Write the cap and the batching into the spec — "under locks on all records" (brief §5.8) is currently unimplementable as stated.

### C7. Soft delete doesn't specify unique-key release — deleted records squat on keys forever, and restore can collide
**Where:** `schema-engine.md` §4 `delete`/`restore`; §2 `RecordUniqueKey` (FK cascade fires only on hard delete).

**Scenario:** A person with unique `emails` is soft-deleted. Their `record_unique_keys` rows remain (nothing in the delete path removes them). Result: nobody can ever create or assert that email again — `DUPLICATE_FOUND` pointing at a deleted record — and `crm_data_quality`'s "unique-key collisions" bucket can't see it because there is no collision, just a ghost reservation. If instead the intended behaviour is to drop keys at delete, then `restore` must re-insert them, and an email taken by a *new* record during the deletion window makes restore fail — a failure mode with no specified error, no MRTR path, and a `crm_record_restore` contract (`out: { record }`) with no way to report it.

**Fix:** Specify it: delete releases unique keys (delete rows in-tx, record them in the delete change's `snapshot`); restore re-claims them and on collision fails with a typed `RESTORE_CONFLICT { attribute, held_by }` plus an MRTR confirmation offering "restore without the conflicting attribute". Same treatment for keys displaced by merge (interacts with C5).

### C8. Approval tokens are consumed non-atomically — one approval can execute twice
**Where:** `auth-and-tenancy.md` §4 ("re-issuing the call with `inputResponses.approval` … completes it"); `protocol-flows.md` F6 ("approval row → consumed"); `contracts.md` `mrtr.ts`; `schema-engine.md` §2 `ApprovalRequest.status`.

**Scenario:** The token flow as specified is: look up `approval_requests` by `continuation_token`, check `status = pending` and role, then run the tool's write path, then mark consumed. Two re-issues of the same approved token in flight (the agent retried; or two agents in the same run both carry it) both read `pending`, both execute the merge/delete/export. Merge is somewhat self-healing (second merge errors on `merged_into_id` already set), but delete, export and schema `define` are not. The spec also never says the approval check and the mutation share a transaction.

**Fix:** Atomic consume in the same transaction as the mutation: `UPDATE approval_requests SET status='consumed', resolved_at=now() WHERE continuation_token=$1 AND status='pending' AND expires_at>now() RETURNING *` — zero rows ⇒ `APPROVAL_REQUIRED`. The mutation and the consume commit or roll back together. State this in `schema-engine.md` §4 (it's an op variant of `applyWrite`, not a pre-check outside it).

### C9. The hash-chained audit log forks under concurrency and serialises every write in an org
**Where:** `auth-and-tenancy.md` §6 ("`entry_hash = sha256(prev_hash ∥ canonical JSON)` per organisation"); `schema-engine.md` §4 step 11.

**Scenario:** Chaining requires reading the previous entry's hash. Two concurrent writes in the same org both read the same tail `entry_hash`, both insert rows with the same `prev_hash` — the chain forks, and `verify-audit-chain.mjs` now reports tampering on an untampered database. The only correct implementation is to serialise chain extension (org-scoped advisory lock or a locked tail-pointer row). That serialisation is (a) unspecified, (b) a throughput ceiling on *every* mutating call in the org (it's inside `applyWrite`'s transaction, so all writes queue behind it), and (c) a new deadlock edge: the audit lock is taken at step 11 after record locks at step 4, so any code path that takes a record lock after touching audit (cascade-delete dependents discovered at step 9, merge's third-party writes per C6) inverts the order and can deadlock with a writer holding the audit lock and waiting on a record lock.

**Fix:** Specify: chain extension is serialised by `pg_advisory_xact_lock(hashtext('audit:' ∥ organizationId))` acquired at a fixed, documented point in the lock order (immediately before the audit insert, and *no* new record/advisory locks may be taken after it — which forces C6's option 1 or pre-computed lock sets). Enforce ordering with a single `LockScope` helper; add the audit lock key to the lock-ordering documentation. Accept and document the per-org write serialisation, or shard the chain per team (per-team tails) to halve contention.

## MAJOR

### M1. `crm_record_at` replay is broken by retention — and by unmerge being "best-effort"
**Where:** `brief.md` §7 ("merge snapshots are hard-deleted by the worker after `DEEPCRM_RETENTION_DAYS`"; "`record_changes` and `AuditLog` are never deleted by product code"); `schema-engine.md` §7.8, §4 delete; `contracts.md` `CrmRecordAt`.

**Scenario:** `crm_record_at(id, at)` reconstructs by replaying changes. But the `snapshot` payload lives **on the change row**, and the retention job hard-deletes merge snapshots after 30 days. Any replay crossing a purged merge/delete point cannot reconstruct the pre-merge state — `record_at` silently returns a state that never existed (survivor's union of values projected backwards), and the property test the brief promises ("replaying changes reproduces `data`", brief §7) is unimplementable. The two brief sentences contradict each other: the change log is both immutable and mutated by retention. Additionally, if unmerge's re-linking is "best-effort", then even before retention, replay across an unmerge diverges from what `data` actually showed.

**Fix:** Pick one: (a) snapshots are part of the immutable change log and are **never** purged (move retention cost to hard-deleting soft-deleted *records*, which the snapshot already covers); or (b) declare `crm_record_at` correct only within the retention window, return a typed error beyond it (`HISTORY_EXPIRED`), and drop the replay-invariant property test to the same window. Delete the contradiction from brief §7.

### M2. Link changes are recorded on one endpoint only — the other record's timeline and feed are blind
**Where:** `schema-engine.md` §2 (`RecordChange.recordId` single, NOT NULL), §4 step 10; `events.md` §1 (`link` → `link.created`); `brief.md` §5.5 (timeline = changes "for a record and its neighbourhood").

**Scenario:** `crm_link(deal → company)` writes one change row. Its `recordId` is either the deal or the company — the other side never sees it. The company's timeline omits "deal linked"; a feed consumer filtering `object_types: ["company"]` misses it entirely; policy filtering (a consumer who may view companies but not deals) gets a row whose `record` summary is the deal — leaking existence or dropping the event, depending on implementation. Same defect for merge re-pointing (C6) and `unlink`.

**Fix:** Write two change rows per link/unlink (one per endpoint, sharing a `link_id` and a `group_id`), or make `recordId` nullable and add `from_record_id`/`to_record_id` columns with the timeline/feed queries unioning both. Update `events.md`'s kind table accordingly. This also fixes M13's sibling: feed filtering by `object_types` then works for link events.

### M3. `schema.changed` events are unrepresentable in the schema that carries them
**Where:** `events.md` §1 ("emitted from a synthetic change row with `record = null`"); `schema-engine.md` §2 (`RecordChange.recordId String @db.Uuid` — NOT NULL, FK `onDelete: Cascade`); `contracts.md` `Change.record: RecordSummary` — non-nullable.

**Scenario:** Three contradictions: (1) a change row must reference a record; there is no record for a schema change. (2) The `Change` contract requires a `RecordSummary`; `events.md` says `record = null`. (3) `ChangeKind` has no `schema` variant, so `kinds` filtering can't express it. As written, `schema.changed` — the documented cue for agents to invalidate their schema cache (protocol-flows F2) — cannot be emitted through the feed at all. Workaround-implementations will either fake a record row (poisoning per-record timelines) or skip persistence (breaking "nothing is emitted that is not a row there").

**Fix:** Add `ChangeKind.schema`, make `recordId` nullable with a check constraint (`(kind = 'schema') = (record_id IS NULL)`), make `Change.record` nullable in the contract, and define `attribute`/`new_value` payload shape (already sketched in events.md). Also: a schema change currently writes **no** audit/change row per the write-path spec — §4's change-row step is record-scoped only. Schema mutations need their own feed/audit rows specified.

### M4. Merge redirect chains — "one hop" redirect breaks after the second merge
**Where:** `schema-engine.md` §7 step 7 ("any read by old id returns the survivor with `redirected_from`… one hop"); `contracts.md` `RecordOut.redirected_from`.

**Scenario:** A merged into B (A.merged_into = B). Later B merged into C (allowed: §7.1 only checks the *inputs* aren't merged). Read by A's id: one hop lands on B, which is itself a tombstone. Does the read follow to C, return B-as-tombstone, or error `MERGED{redirect_to: B}` pointing at a tombstone? Unspecified — and all three are wrong in different ways (silent chain-walking is unbounded; returning B presents a dead record as a redirect target; erroring strands every stored reference to A). Integrations store ids; ids get merged twice; this is routine.

**Fix:** Resolve redirects transitively at read (`WITH RECURSIVE` or a maintained `canonical_id` column updated at merge time — preferred: `records.canonical_id` set to the final survivor for every loser in the chain, so reads are O(1) and `redirected_from` reports the original id). Also define what `record_links` to A mean after A→B→C (they were re-pointed to B at the first merge, then to C at the second — fine — but say so) and what unmerge of B→C does to A's canonical pointer (A.canonical_id must be recomputed to B).

### M5. Merge can create key/data divergence by design — assert then "finds" values the record doesn't have
**Where:** `schema-engine.md` §7 step 3 vs §3 (unique keys are the normalised projection of `data`).

**Scenario:** Single-value unique attribute (or a multi-value one where the field choice keeps the survivor's set): merge moves the loser's key to the survivor "where survivor lacks them; drop the rest" — but the survivor's `data` keeps the survivor's value. Now `record_unique_keys` says the survivor owns `anna@asahi.eu` while `data.emails` doesn't contain it. `crm_record_assert(match_attribute: emails, anna@asahi.eu)` updates the survivor, but the asserted value isn't in its data; `crm_record_get` by that email returns a record that doesn't display it; search content excludes it. The engine's core invariant — key table mirrors `data` — is violated by the engine itself.

**Fix:** Rule: keys follow data, no exceptions. Merge may only keep a loser's key if the loser's value is also unioned into the survivor's `data` (for single-value attributes this requires field-choice semantics that *replace* the survivor value, or promotion to multi). Keys whose values didn't survive are dropped **and recorded in the merge snapshot** (needed for C5's unmerge anyway).

### M6. Cardinality and `on_delete` enforcement races: dependents are discovered after the lock batch
**Where:** `schema-engine.md` §4 steps 4 and 9, `delete` semantics.

**Scenario:** Step 4 locks "every record touched" up front, but delete's dependents (cascade targets, restrict blockers) are discovered by reading `record_links` — which happens after locking, per the step order. A concurrent `crm_link` that locks its endpoints can insert a new link to the deleting record after the delete's check but before commit: `restrict` is violated (record deleted despite a live link), or a cascade misses the new dependent (orphan link to a deleted record). Conversely if delete re-checks after locking, the *linker* must also re-check "target not deleted/merged" under the same locks — `record_reference` validation does this at step 3, *before* the step-4 locks, so it's check-then-act too.

**Fix:** Specify the discipline: for link/delete ops, (1) take endpoint locks in sorted id order, (2) *then* perform existence/deleted/restrict checks and dependent discovery, (3) perform writes. Validation that depends on locked state must run after locking, not at step 3. Merge (§7.1's "none deleted/merged") has the same ordering bug and the same fix.

### M7. Queue starvation and no-crash-recovery: the queue spec is three indexes and good intentions
**Where:** `architecture.md` §1 (worker "poll loop over queue_jobs"; jobs: reindex, dedup-scan, bulk-assert/export, change-deliver, retention); `schema-engine.md` §2 `QueueJob`.

**Scenarios:** (a) *Starvation:* one global FIFO (`@@index([status, visibleAt])`), no priority, no per-tenant fairness, no per-type concurrency. A 10,000-row bulk assert enqueues 10,000 `record.reindex` jobs; every other tenant's webhook delivery and every dedup scan waits behind them. `change.deliver`'s 30 s debounce becomes 30 s + queue depth. (b) *Crash wedge:* `lockedAt`/`lockedBy` exist but no visibility timeout, heartbeat or reaper is specified; a worker that dies mid-job leaves `status=running` forever — a bulk import that never completes and (because `QueueJob.idempotencyKey` is unique) can't be re-enqueued. (c) *Bulk retry duplication:* `crm_records_bulk_assert` rows carry no per-row idempotency keys (`contracts.md` — only a job-level `reason`), and job-level retry reprocesses "their current batch" (F7) without any row-dedup, so retried batches double-apply non-unique patches (e.g. multi-value unions are idempotent, counter increments or appends via JSON are not — and activities with no `external_ref` duplicate outright).

**Fix:** Specify the claim protocol (`SELECT … FOR UPDATE SKIP LOCKED` with a lease: `locked_at < now() - lease ⇒ reclaimable`, heartbeat on long jobs), add `priority` and per-type worker pools with per-tenant round-robin, require per-row idempotency keys in bulk payloads (derive as `sha256(match_attribute ∥ normalized ∥ row_hash)` when absent) stored so batch retries skip completed rows, and make `change.deliver`/`record.reindex` high-priority lanes bulk jobs can't flood. Also add the missing `attribute.index` job to the worker list (architecture §1 omits the job schema-engine §5 requires).

### M8. pgvector/HNSW at scale: tenant-filtered recall collapse, churn bloat, no model migration path
**Where:** `schema-engine.md` §2 `RecordSearch` (`hnsw (embedding vector_cosine_ops)`, `vector(1024)`), §8; `brief.md` §5.7.

**Scenarios:** (a) *Recall collapse:* HNSW has no tenant awareness; search does ANN top-k then filters by tenant/policy post-retrieval (§5.7: "policy-filtered post-retrieval"). In a multi-tenant index, a tenant holding 0.1% of vectors gets ~0 of the global top-50 — semantic search silently returns nothing for small tenants exactly when the index is biggest. (b) *Churn:* every record write enqueues a reindex; each re-embed is delete+insert in the HNSW graph. HNSW handles updates poorly — dead-entry accumulation degrades recall and bloats the index; no vacuum/rebuild strategy is specified. (c) *Model change:* `embedding_model` is recorded but nothing rebuilds embeddings on model upgrade, and `vector(1024)` is hard-coded while `EMBEDDING_DIMENSIONS` is config — a model with different dims is a column-altering migration the docs don't mention. (d) 1024-dim × 4 B = 4 KB/row plus graph overhead; no memory/`maintenance_work_mem`/`ef_search` guidance; `m`/`ef_construction` defaults unexamined.

**Fix:** Specify: iterative ANN scan (`hnsw.iterative_scan = strict_order` with the tenant filter in the query, PG17/pgvector ≥0.8) or per-tenant partitioning of `record_search`; an `ef_search` setting; a scheduled `reindex` + periodic index rebuild policy for churn; and an embedding-migration job (`embed.model_migrate`) that dual-writes/re-embeds lazily by `embedding_model != current`. Decide per-tenant vs shared index now — retrofitting is a full rebuild.

### M9. Search-document staleness: one-hop content never rebuilds when the neighbour changes
**Where:** `schema-engine.md` §8 (`buildSearchContent` includes "for each active link the relation `forward_name` + target `display_name`"); §4 step 12 (reindex enqueued only for the written record).

**Scenario:** Company renamed "Asahi Europe" → "Asahi Group Europe". Its reindex job updates the company's search doc. Every person whose content embeds "… at Asahi Europe" keeps the stale string indefinitely — until that person happens to be edited. Keyword search for the new name misses all its people; the embedding is likewise stale. The fan-out (rename → reindex all inbound-linked records) is unspecified, and naive fan-out re-FLOODS the queue (M7) — a company with 5,000 people emits 5,000 reindex jobs per rename.

**Fix:** Specify fan-out: on `display_name` change, enqueue one `record.reindex_neighbours {recordId}` job that re-renders inbound-linked records' content in batches (re-embedding only when the rendered text actually changed — store a `content_hash` to skip no-op embeds). Document the staleness window as eventual-consistency semantics in the tool description for `crm_search` ("recently renamed linked records may not match for up to N seconds").

### M10. `is_indexed` CONCURRENTLY index management will litter the database and crush write throughput
**Where:** `schema-engine.md` §5 ("`CREATE INDEX CONCURRENTLY records_<objtype>_<slug> ON records ((data->>'slug')) WHERE object_type_id = '…'`"), §3 `isIndexed`.

**Scenarios:** (a) *Name collisions:* `records_<objtype>_<slug>` with 63-char slugs each blows Postgres's 63-byte identifier limit → silent truncation → two attributes mapping to one index name → the second `CREATE` errors or, worse, `IF NOT EXISTS` no-ops leaving one attribute unindexed forever. (b) *Crash residue:* CONCURRENTLY can't run in a transaction; a worker dying mid-build leaves an `INVALID` index that is never used but **is** maintained on every write, and blocks naïve retries (`relation already exists`). No detection/cleanup is specified. (c) *Write amplification:* every `records` UPDATE maintains every expression index on the table even when the indexed attribute didn't change (HOT updates defeated because `data` itself changed). The template seeds 10 indexed attributes; tenants add more; the hottest table pays O(#indexes) per write. (d) The unset path (`is_indexed: true → false`, attribute archive, object-type archive) never says `DROP INDEX CONCURRENTLY` — indexes accumulate forever. (e) Two concurrent `attribute.index` jobs for the same attribute (retry + manual re-toggle) race.

**Fix:** Name indexes `idx_records_<attributeId first 8 hex>` (stable, unique, short); the job must start by dropping any `INVALID` index of that name; specify `DROP INDEX CONCURRENTLY` on unset/archive; add a per-tenant cap on indexed attributes with `LIMIT_EXCEEDED`; document the write-amplification trade-off in the `crm_attribute_define` description (agents set `is_indexed` casually — the description is the only guardrail). Consider one shared GIN index + `jsonb_path_ops` first (already present) and expression indexes only for proven-hot filters.

### M11. `schema_version` cache invalidation across processes is hand-waved — writes validate against stale schemas
**Where:** `architecture.md` §5 ("`schema_version` is bumped inside the same transaction… caches key on it"); `schema-engine.md` §4 step 2 ("`loadSchema(tenant)` cached by `teams.schema_version`"); `auth-and-tenancy.md` §3 (60 s in-process tenant cache).

**Scenario:** Two API replicas + a worker. Replica 1 archives attribute `fax` (version 41 → 42). Replica 2 holds schema v41 in memory. Unless every request re-reads `teams.schema_version` (a DB hit the docs never mention) or there is a TTL/pubsub (unspecified), replica 2 keeps validating against v41: accepts writes to an archived attribute, rejects new attributes with `UNKNOWN_ATTRIBUTE`, evaluates matching rules that no longer exist. The 60 s tenant cache has the same shape: a deleted/archived tenant keeps being served for up to a minute. The failure window is unbounded because no invalidation mechanism is specified at all — "caches key on it" describes the key, not the invalidation.

**Fix:** Specify: every request loads `(schema_version)` in the same query that resolves the tenant (single indexed row read — cheap), and the in-process schema cache is keyed by `(team_id, schema_version)` with no TTL — a version bump is self-invalidating. No cross-process pubsub needed. State explicitly that the 60 s tenant cache caches *id resolution only*, never schema or policy state. Policy rules have the identical staleness problem and no version at all — add `teams.policy_version` bumped with rule/binding changes, same mechanism.

### M12. Policy evaluation ignores scope specificity — record-level exceptions are impossible
**Where:** `auth-and-tenancy.md` §4 step 3 ("order by `priority` desc; first matching rule wins except deny at equal-or-higher priority"); `docs/spec/policy-defaults.json`.

**Scenario:** Rules are ordered by priority only. A team-wide deny (priority 0) and a record-scoped allow (priority 0) — the deny wins ("any deny at equal-or-higher priority"). So the product cannot express "members can't export *except this one list*", the single most common real policy. Raising the allow's priority works, but then an org-wide deny at the default priority can't override it — specificity and priority fight over one axis. Worse, `conditions` (`{"sensitivity": "restricted"}` in the seeded rules) has no defined evaluation semantics anywhere — what it matches against, how multiple conditions combine, whether unknown keys error.

**Fix:** Add scope specificity to the ordering: sort by (priority desc, scope specificity desc — record > list > object_type > team > organization), then deny-overrides *within the winning tier only* (a broader deny should not silence a narrower allow unless its priority is strictly higher). Document it with the seeded defaults as worked examples. Define `conditions` as exact-match conjunction against a named context bag (`{sensitivity}` for attribute resources), unknown keys ⇒ reject the rule at write time.

### M13. Tenant provisioning races seed duplicate default policies (and the feed cursor default dumps all history)
**Where:** `protocol-flows.md` F10; `docs/spec/policy-defaults.json` (no unique constraint backing); `schema-engine.md` §2 `PolicyRule` (only a non-unique index); `contracts.md` `CrmChangesSince` ("omit for the oldest retained change").

**Scenarios:** (a) Two concurrent first-calls for a new team: both upsert org/team (fine), both `seedDefaultPolicies` — no unique constraint on `(team, resource_type, action, effect, priority, scope)` exists, so the team's policy table gets doubled rows. Evaluation tolerates dupes mostly by luck (idempotent effects), but the approval-required deny now exists twice and any later edit updates one row. Templates survive by slug uniqueness; policies don't. (b) `crm_changes_since` with no cursor returns "the oldest retained change" — and changes are never deleted — so a new consumer's first call pages through the entire history of the tenant. An agent that just wants "what changed since I started" gets a multi-thousand-event backfill and (per C1's cursor) a meaningless starting point.

**Fix:** (a) Serialise provisioning with `pg_advisory_xact_lock(hashtext('provision:' ∥ externalTeamId))` and make policy seeding `INSERT … ON CONFLICT DO NOTHING` over a real unique constraint, or make seeding idempotent by checking existence inside the lock. (b) Change the no-cursor default to "now" (first call returns only a fresh cursor, `has_more: false`), with an explicit `from: beginning` opt-in.

### M14. `normalizedValue` will exceed the btree row-size limit — unique text attributes crash on long values
**Where:** `schema-engine.md` §2 `RecordUniqueKey.normalizedValue` (plain text, in a `@@unique` btree), §3 (`text` default `maxLength` 4000; `rich_text` 100k excluded, but `text`/`url` are not length-capped for uniqueness).

**Scenario:** A unique `text` attribute (the type registry allows `supportsUnique` semantics for text — and `external_ref` in the system template is exactly this, `maxLength` 300 — safe; but any custom unique text at the 4000 default) receives a 3,500-character value. Postgres btree index tuples max out around 2,704 bytes: the insert fails with `index row size exceeds maximum`, the whole write path 500s with an untyped `INTERNAL`, and the attribute can never hold long values — discovered in production, by a customer.

**Fix:** Store `normalizedValueHash bytea/text` (sha-256 hex) in the unique index, keep the full normalized value in a non-indexed column for evidence display; uniqueness on `(attributeId, hash)`. Cap raw stored length. This also future-proofs against locale/normalisation producing expansion.

### M15. Relation-type archive is an unbounded mass mutation with no specified mechanics
**Where:** `mcp-surface.md` §2 ("`crm_relation_type_archive` — links are kept but inactive"); `schema-engine.md` §2 `RelationType.archivedAt`; §4 step 9 (projections).

**Scenario:** "Kept but inactive" — does archival set `active_until` on all links (a single UPDATE over potentially millions of rows inside one transaction, emitting per-link change rows per §4 step 10 — unbounded txn, lock storm, feed flood), or does it leave links and filter at read? What happens to `record_reference` projections backed by this relation (`projectionAttributeSlug`)? Are they stripped from every record's `data` (mass rewrite), left stale (drift), or erroring reads? None of this is specified, and every option has a different operational blast radius.

**Fix:** Specify: archive is metadata-only; links remain with `active_until NULL` but reads treat links of archived relation types as ended (filter at query), projections are computed-at-read (per C6 option 1) or lazily cleaned by a worker job; no change rows are emitted for archival itself beyond one `schema.changed` event. If projections stay materialised, archive becomes a Task.

### M16. `assert` on a multi-value unique attribute is undefined
**Where:** `schema-engine.md` §4 assert; `contracts.md` `CrmRecordAssert`; templates (`person.emails`: `is_multi + is_unique`, and it's the documented assert target).

**Scenario:** The canonical call `crm_record_assert(match_attribute: "emails", data: { emails: ["a@x", "b@y"] })` — which element is the match key? If any, what happens when `a@x` belongs to record 1 and `b@y` to record 2 — update both? Error? Merge hint? If the first element, that's a hidden rule agents can't discover. The F4 example works only because it passes one email.

**Fix:** Specify: match key = the first element of the attribute's value in `data` (say so in the tool description), and if *any other* element resolves to a different record, fail with `DUPLICATE_FOUND { candidates }` naming both records — the agent's cue to merge. Add the multi-record case to F4.

## MINOR

- **m1 — Debounce window inconsistency.** `schema-engine.md` §4 step 12: idempotency `deliver:<teamId>:<minute>`; `events.md` §3: `visibleAt = now + 30 s`, `floor(now/30s)`. Pick one; with the minute variant a 30 s-visible job's idempotency key can collide with the next window's enqueue (unique `idempotencyKey` ⇒ second enqueue dropped, delivery delayed a full minute).
- **m2 — No-op assert still bumps `version`** (F4: "patch applied, version+1 (no-op patch ⇒ no change rows)"). Version without change rows desynchronises `version_at` in `crm_record_at` and makes `expected_version` concurrency noisier than necessary. Skip the version bump when the normalised patch is empty.
- **m3 — `tools/list` etag = `schema_version` is meaningless** (`mcp-surface.md` §0.1, F2): the 47 tools are static; schema changes don't alter them. Clients will refetch a byte-identical tool list on every schema bump. Etag on the *server build*; `schema_version` belongs on `crm://schema` only (where it already is).
- **m4 — `IdempotencyReplay` has no expiry mechanism.** Contracts promise "within 24h" but nothing deletes rows (retention job covers soft-deletes and merge snapshots only). Either specify cleanup (and accept that replay after 24h re-executes — say so in the key's description) or keep forever and fix the description.
- **m5 — Advisory-lock key space is 32-bit `hashtext`.** `hashtext(recordId)`, `hashtext('webhook:'∥id)`, `hashtext('audit:'∥org)` share one int4 domain: ~4e9 buckets across all namespaces ⇒ birthday collisions at ~77k locked entities, and *cross-namespace* false sharing (a record and a webhook serialising against each other). Use `pg_advisory_xact_lock(namespace_int, hashtext(id))` (the two-int form) with a namespace constant per concern.
- **m6 — Approval self-service.** F6: the re-issue carries "the admin's delegation" *through the same agent*. Any agent that can obtain an admin-delegated call context can approve its own requests (request and approval share `runId`/`toolCallId` provenance with no separation check). If separation of duties matters, require `resolverUoaUserId ≠ onBehalfOf` of the request, and record both in the audit row.
- **m7 — `restore` of cascade-deleted trees is unspecified.** Delete cascades soft-delete dependents (`schema-engine.md` §4); restore says "reverses within retention" — does it restore the cascade set (from where — the delete change's snapshot is on the root only)? Define restore semantics for the cascade set or record per-dependent delete changes with a shared `group_id` restore can follow.
- **m8 — `crm_record_at` omits links.** `contracts.md` `CrmRecordAt` returns only `data` + `version_at`. Links are time-stamped (`active_from/until`) and reconstructable; "the record as it was at a timestamp" that can't say what it was linked to is half the feature. Add `links` (filtered by `active_from ≤ at < active_until`) or rename the tool's promise in its description.
- **m9 — Timeline `hops: 1` policy leak.** `brief.md` §5.5: a company's timeline includes its people's activities. If the caller may view the company but not a person (record-scope deny), the one-hop items must be post-filtered — unspecified. Say it, and say what `TimelineItem` looks like when the `about` record is denied (omit vs. redact).
- **m10 — `display_name` is derivable-but-stored with no drift repair.** Primary attribute archived or `primary_attribute` changed ⇒ every record's `display_name` is stale until edited (same class as M9). Either include in the reindex fan-out or compute at read.
- **m11 — Worker job list drift.** `architecture.md` §1 omits `attribute.index` (schema-engine §5) and any embedding-migration job (M8). The topology diagram is the thing implementers will scaffold from.
- **m12 — Webhook secret rotation unspecified.** `crm_webhook_set` upserts on `@@unique([org, team, url])` and returns `secret` "shown once on creation" — rotation path (new secret, overlap window) undefined; a leaked secret means delete+recreate with a delivery gap. Add `rotate_secret: boolean`.
- **m13 — Webhook catch-up is unthrottled.** After an outage, re-enable resumes from `last_delivered_seq` with ≤500-event batches back-to-back — a multi-day backlog becomes a self-DoS of the receiver. Specify a max catch-up rate (or a `max_events_per_batch`/`max_batches_per_run` cap) and a receiver-visible `backlog_remaining` field.
- **m14 — `Change.seq` typed as string, cursor typed as opaque string, but `events.md` says "decimal string of the last seq".** Fine — until someone base64s it (query cursors are base64 elsewhere). One cursor encoding spec for all tools; say whether feed cursors are raw decimal or opaque.

## What breaks first

In deployment order: **C1** (the first bulk import skips feed events and nobody notices), **C3/C2** (the first concurrent sync produces duplicates or phantom errors), **C9** (the first two parallel writes fork the audit chain), **C4** (the first duplicate a `block` rule was bought to prevent), **M8a** (the second tenant's semantic search returns nothing). Every one of these is a doc-level fix — a changed paragraph, a constraint, a lock-ordering rule — made now rather than a postmortem later.
